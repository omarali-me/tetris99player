Tetris 99 Bot Field Guide

How the bot decides, how a microcontroller becomes a Nintendo controller, and how 6 million pixels a frame turn into ten columns of symbols. Written from the source as it stands in the repository today.

The pipeline in one picture

Every piece the bot places goes through the same five stages. Keep this picture in mind, because each chapter below zooms into one part of it.

1 · Cold Clear

Cold Clear is a versus Tetris bot written in Rust by MinusKelvin. Its job is to answer one question, over and over: given this board, this piece, the hold slot, and the next six pieces, where should this piece go? Everything in it serves that question. Three parts do the work: a move generator that lists every reachable placement, an evaluator that scores the board a placement leaves behind, and a search that looks several pieces ahead through the queue.

1.1 Board and pieces

The board is 10 columns by 40 rows. Only 20 are visible on screen; the rest is headroom so a piece can spawn and be evaluated even when the stack is high. Each row is stored as an integer where bit x is set when column x is filled. This is called a bitboard, and it makes the common questions cheap: a row is full when it equals 0b1111111111, a cell is filled when row >> x & 1 is 1, and clearing lines is deleting integers from a list.

Our own tetris99/engine/board.py uses the identical scheme, which is why the two sides can compare boards cell for cell.

A falling piece is a kind, a rotation state, and the position of its rotation point. The four cells are offsets from that point. North orientation is the table below; the other three are the same offsets rotated, which is why the code stores only seven shapes and derives 28.

piececells relative to the rotation point (x right, y up)color
I(-1,0) (0,0) (1,0) (2,0)cyan
O(0,0) (1,0) (0,1) (1,1)yellow
T(-1,0) (0,0) (1,0) (0,1)purple
L(-1,0) (0,0) (1,0) (1,1)orange
J(-1,0) (0,0) (1,0) (-1,1)blue
S(-1,0) (0,0) (0,1) (1,1)green
Z(-1,1) (0,1) (0,0) (1,0)red

Rotation follows SRS, the Super Rotation System that every guideline Tetris uses. When a rotation would collide, the piece tries up to five alternative offsets called kicks, in a fixed order. Each rotation state has a table of five "rotation points"; the kick to try is the difference between the old state's point and the new state's point. That is how a T piece slides under an overhang to make a T-spin: the plain rotation collides, the second or third kick lands it in the slot. The I piece has its own tables, and the O piece's "kicks" are all identical so it visibly rotates in place.

Pieces spawn with the rotation point at column 4, row 19, or row 20 if 19 is blocked. This detail matters for us because the tracker looks for the spawned piece in exactly that zone.

1.2 Finding every placement

The function find_moves in libtetris/src/moves.rs takes a board and a spawned piece and returns every distinct position the piece can lock in, each with the shortest input sequence to get there. It is a shortest-path search over piece states, where a state is position plus rotation and the edges are the five moves: left, right, clockwise, counter-clockwise, and sonic drop (soft drop to the floor).

Two tricks make it fast.

  • Skipping the air. If every column is below height 16, the piece can reach any column and rotation without touching the stack, so the search starts from all those positions at once instead of walking there one tap at a time. Each starting position is sonic-dropped and locked to produce the "obvious" placements immediately.
  • A priority queue by input time. From every dropped position it then tries the five moves again, so it discovers tucks and spins that are only reachable after landing. States are popped cheapest first, so the first time a locking position is found, its path is already the shortest. A hash set of visited states stops it re-exploring.

The output includes the path, which is the movement list our executor replays. That is why a Cold Clear move can say "left, clockwise, drop, clockwise" and be certain it ends where it promised.

There are movement modes. We use 0G, meaning the piece does not fall while we move it, which is true for the first minutes of a Tetris 99 game. In 20G mode the piece is on the floor the moment it spawns and only floor-level moves count; that is how late-game speed works, and it is a one-field switch if we ever need it.

1.3 Scoring a board

After each placement the evaluator, in bot/src/evaluation/standard.rs, produces two numbers. The value describes the board that is left: how safe and productive it looks. The reward describes what the placement itself earned. Both are weighted sums of features, and the weights are the numbers in config/weights.json. The value of a line of play is the sum of rewards along the way plus the value of the final board.

Value features (the shape of the stack)

height
the tallest column, times a negative weight
top_half, top_quarter
extra penalties that only switch on above row 10 and row 15: max(h−10,0) and max(h−15,0). Panic grows sharply near the top.
well
the lowest column is called the well. Its depth is how many rows are completely filled except for that column. Depth is rewarded up to max_well_depth, and well_column says how much the bot likes the well in each column. The default table prefers columns 4 and 6 in the middle, slightly dislikes column 8.
bumpiness
the sum of height differences between neighbouring columns, ignoring the well. Also the sum of squares, so one tall spike hurts more than several small steps.
cavity_cells
empty cells with something above them that cannot be reached from the side. Real holes. The single largest penalty, −173 each.
overhang_cells
empty cells under a lip that could still be filled by sliding in from a lower neighbour. Cheaper than a cavity.
covered_cells
filled cells sitting above a hole. Each one is a cell you must clear before the hole is fixable.
row_transitions
how many times a row switches between filled and empty as you scan across, computed with a bit trick: (row | 1<<10) ^ (1 | row<<1) and count the ones. Jagged rows are bad.
tslot
the interesting one. The evaluator runs pattern matchers for T-spin setups: an open slot with a lip on one side, a TST twist shape, a "fin". If it finds one it simulates cutting the T out and scores how many lines that would clear, using tslot[lines]. It repeats this up to as many T pieces as it expects soon, judged from the bag and the hold slot. This is why the bot builds T-spin slots on purpose before a T arrives.
back_to_back
a bonus for currently holding back-to-back status, since the next Tetris or spin will send more.

Reward features (what the placement did)

clear1..clear4
reward per clear size. Singles and doubles are negative in versus play: they spend stack for little attack.
tspin1..3, mini_tspin1..2
T-spin rewards. Minis are penalised because they waste the T.
b2b_clear
bonus when a clear keeps a back-to-back chain alive
combo_garbage
weight times the garbage the combo actually sends, from a lookup table
wasted_t
a T piece placed without spinning
move_time
a small penalty per input, plus 40 for any clear, standing in for the line-clear animation delay
jeopardy
scaled by height above row 10 and by move time when timed_jeopardy is on: a tall stack is more dangerous when the move is slow and garbage is coming
perfect_clear
+999, rarely reachable but decisive when it is

The attack table these rewards chase is the guideline one: a double sends 1 line, a triple 2, a Tetris 4, a T-spin single 2, T-spin double 4, T-spin triple 6, plus back-to-back bonuses and combo garbage. A T-spin double sends as much as a Tetris while using two lines instead of four. That single fact explains most of the bot's style.

Where incoming garbage enters. Cold Clear's pick_move takes the sorted list of candidate moves and, when we tell it garbage is incoming, skips any move whose middle columns plus the incoming lines would exceed row 20. If no move is safe, it falls back to the one with the largest attack spike, hoping to cancel. That is the incoming number our loop now passes from the garbage meter.

1.4 The search

Evaluating a single placement is not enough. A placement that looks slightly worse now can set up a Tetris two pieces later. So the bot searches: it builds a graph of futures over the known queue and keeps improving it until asked for an answer. The file that does this is bot/src/dag.rs, and its own header comment calls it "by far the most complicated file in Cold Clear".

Generations and deduplication

Nodes are grouped into generations, one per piece placed. Generation 0 is the current board. Generation 1 holds every board reachable by placing the next piece, or the hold piece instead. When two paths reach the same board, they share a node. "Same" is decided by a SimplifiedBoard key: the filled rows, back-to-back status, combo, which pieces remain in the bag, and which piece is in reserve. Merging these transpositions is a large saving, because Tetris is full of them: place A then B, or B then A, often leaves the same stack.

Selection: the Monte Carlo part

A think cycle starts at the root and walks down to a leaf, choosing a child at each node. The choice is random but biased. At every node the children are already sorted best to worst, and each child gets a weight

weight = (child_value − worst_value + 10)²  /  (rank² + 1)

then one is sampled in proportion. Better children are picked far more often, but a mediocre child still gets visited now and then, so the search does not tunnel on its first guess. When it hits a speculated node, where the next piece is unknown, it picks one of the possible bag pieces uniformly and continues into that branch. The leaf is marked so no other thread expands it at the same time.

Expansion

A worker thread takes the marked leaf and expands it: it runs find_moves for the next piece and again for the hold piece, evaluates every resulting board, and hands back a list of children. If the next piece is unknown but speculation is on, it does this once per piece still possible in the bag and stores the groups separately. The default bot in our loop does this on 2 threads.

Backpropagation

New children change the value of their parent, and that change travels up. A node's value becomes the best of its children's value + reward. For a speculated node it is the average over the possible pieces, since each is equally likely. Nodes that lead only to death (no legal placement) are dropped, and a death evaluation is a flat −1000. Because a node can have several parents, the update runs breadth-first up the generations and each node is refreshed once.

Answering

When we request a move, the bot finishes any in-flight thinks, sorts the root's children, lets pick_move apply the incoming-garbage filter, and returns the top candidate with its path and expected cells. Then advance_move deletes generation 0 and everything not under the chosen child, and the chosen child's generation becomes the new root. Nothing below is recomputed: the bot carries its tree forward, which is why it should be left alone to think between requests.

Two options bound the work: min_nodes is the smallest tree it will answer from, max_nodes the point where it stops growing. We set max_nodes to 100,000. The depth in our log is how many generations deep the chosen line was verified; 8 is normal with 50 ms of thinking.

1.5 Talking to it

The bot lives on its own thread and is driven by messages: NewPiece, SuggestMove(incoming), PlayMove, and Reset. The C API in c-api/src/lib.rs wraps these, and tetris99/engine/coldclear.py wraps the C API with ctypes, Python's built-in way of calling C functions in a shared library. The binding must describe every struct field in order and size, which is why CCWeights in Python mirrors the C struct line for line. Get one field wrong and the numbers silently shift.

The rhythm our loop uses, and the reason it matters:

  1. At spawn, tell the bot any newly revealed queue piece.
  2. Request a move with the incoming garbage count. Poll until it arrives.
  3. Compile and send the inputs. Predict the resulting board.
  4. Do nothing. The bot keeps thinking on its tree during the drop and clear animation.
  5. At the next spawn, compare the observed board with the prediction. If they differ, garbage arrived or something went wrong: relaunch the bot from the observed board.

Relaunching rather than resetting is deliberate. A reset with a request in flight can hand back a move computed for the old board; a fresh launch cannot.

2 · The controller

The Switch will only listen to controllers it recognises. We are not breaking any of that. We are building a device that is, in every way the Switch can observe, a licensed wired gamepad. To see why that works you need a little of how USB introduces devices to hosts.

2.1 How USB devices introduce themselves

USB is strictly host and device. The host (here, the Switch) asks, the device answers. When you plug something in, the host runs enumeration: it reads a series of descriptors from the device, which are small binary tables that say what the device is.

  • The device descriptor carries a 16-bit vendor ID and product ID, plus string indexes for the manufacturer and product name. Vendor IDs are assigned to companies; HORI's is 0x0F0D.
  • The configuration and interface descriptors say what kind of device it is. Class 3 means HID, the Human Interface Device class that covers keyboards, mice, and gamepads.
  • The HID report descriptor is a tiny program that describes the layout of the data packets the device will send: how many buttons, how many axes, how many bits each.

After enumeration the host polls the device on a fixed interval, typically every 8 ms for a gamepad, and the device answers each poll with one input report in the layout it declared. That is the entire protocol for a simple gamepad. There is no session, no authentication, no encryption, just descriptors and then a stream of reports.

2.2 The 8-byte report

Here is the report descriptor the firmware library declares, decoded. It comes from SwitchControlLibrary.cpp and it is the same layout the real HORI Pokken pad uses.

The descriptor's own words, for the buttons part: USAGE_PAGE (Button), USAGE_MINIMUM (1), USAGE_MAXIMUM (16), REPORT_SIZE (1), REPORT_COUNT (16), INPUT (Data,Var,Abs). Read it as: sixteen one-bit variables, each an absolute button state. The hat switch is one four-bit value from 0 to 7 for the eight directions, 8 for centred, with UNIT (degrees) and a physical range of 0 to 315 so the host can interpret it as an angle. The sticks are four bytes, 0 to 255, with 128 as centre. We never move the sticks; the d-pad is the hat.

The bit order in that table is exactly the Button flags enum in tetris99/control/protocol.py, which is why our PC-side code can hand the Arduino a raw mask.

2.3 Why the Switch believes it

The Switch keeps a list of USB controllers it accepts, keyed on vendor and product ID. Licensed third-party wired pads, including the HORI Pokken Tournament Pro Pad (0x0F0D / 0x0092), are on it. Those pads are plain HID gamepads. Nintendo's own Pro Controller, by contrast, speaks a proprietary protocol with a handshake, and Joy-Cons pair over Bluetooth with their own exchange. So the trick is not to impersonate a Pro Controller; it is to present the identity of a device that was designed to be simple.

Three things have to line up, and the firmware README walks through each:

  1. Identity. The Arduino core builds the device descriptor from boards.txt. Editing the VID, PID, manufacturer, and product strings there makes the compiled sketch enumerate as "HORI CO.,LTD. POKKEN CONTROLLER".
  2. Interface. The library registers an HID interface with the report descriptor above through the Arduino core's PluggableUSB mechanism, so the sketch does not have to write USB code.
  3. Behaviour. The sketch answers polls with sensible reports: sticks centred, hat at 8, buttons 0, from the moment it boots.

The Switch also has a setting, Pro Controller Wired Communication, that gates USB controllers entirely. It must be on.

The hardware requirement follows from all this. The chip must have USB device hardware that firmware controls. The ATmega32U4 in a Pro Micro or Leonardo does. An Uno's USB is a separate chip that only ever presents a serial port, which is why it cannot do this.

2.4 PC to Arduino

The Arduino's USB port is busy being a gamepad for the Switch, so the PC talks to it over a second link: the chip's hardware UART on pins TX and RX, wired to a USB-to-TTL adapter on the PC side. Three wires: TX to RX, RX to TX, ground to ground. On Linux the adapter appears as /dev/ttyUSB0 and pyserial opens it like a file.

The protocol on that wire is three bytes per command: an opcode and a 16-bit argument. SET replaces the held button mask. PRESS holds a mask for a fixed press length and releases it. HAT sets the d-pad. WAIT delays the next queued command by N milliseconds. RELEASE lets go of everything. PING gets a one-byte echo, which the loop uses on startup to confirm the board is alive.

The Arduino keeps a queue of these and executes them with its own millisecond clock. That is a design choice worth understanding: serial delivery from a PC has jitter of a few milliseconds, and the operating system can pause a Python process for longer. If the PC did the timing, a "hold left for 300 ms" could become 280 or 340. If the Arduino does it, it is 300. The PC sends the whole action list for a piece in one burst and gets on with reading frames.

2.5 Timing and DAS

The game samples inputs once per frame at 60 Hz, so anything shorter than one frame, 16.7 ms, can be missed. Our tap is 34 ms, about two frames, with a 34 ms gap so two taps in a row are seen as two.

Holding a direction does something different from tapping it. After a delay, called DAS for delayed auto-shift, the game starts moving the piece repeatedly at a fixed rate, called ARR. Tetris 99 fixes both; you cannot tune them in settings. The executor exploits this: a run of two or more moves in the same direction that ends against a wall or the stack becomes a single hold long enough to reach it. One input, and the piece arrives at the wall regardless of how many cells that was. The DAS_MS constant is the hold length; we measure the real DAS and ARR once the hardware is here and set it with margin.

Every placement is at most: hold, one or two rotations, a horizontal move or DAS, optionally a soft drop and one more move for a spin, then hard drop. Five or six inputs, well under half a second, which leaves the bot most of the piece time to think.

3 · Vision with OpenCV

OpenCV is a large library, and the bot uses a small, well-chosen slice of it: reading frames from a capture device, converting colour spaces, and drawing overlays for debugging. The rest is plain numpy. This chapter goes from a frame in memory to a spawn event in the tracker.

3.1 What a frame is

A frame is a numpy array of shape (1080, 1920, 3) and type uint8: 1080 rows, 1920 columns, three bytes per pixel. The bytes are in BGR order, blue first, which is an OpenCV convention inherited from early camera drivers and a classic source of swapped-colour bugs. Indexing is frame[y, x], row first, so the pixel at screen position (x=100, y=50) is frame[50, 100].

Size sets the design. One frame is 6.2 MB. At 60 frames a second that is 373 MB of pixels a second flowing through Python. Touching every pixel every frame is out of the question, so the vision code never does: it samples about 200 tiny patches at known positions and ignores the other 99.9 percent of the image. Slicing a numpy array, frame[y-3:y+4, x-3:x+4], creates a view, not a copy, so even that costs almost nothing.

3.2 Getting frames in

On Linux a capture card is a V4L2 device, /dev/videoN. cv2.VideoCapture(N, cv2.CAP_V4L2) opens it and read() returns the next decoded frame. Two settings in capture.py matter.

  • MJPG. USB 2 carries about 480 megabits a second. Raw 1080p60 is over 2,000. So the cheap cards compress each frame to JPEG on the way out, and OpenCV decodes it on the way in. Asking for the MJPG pixel format is what makes 1080p60 possible; the alternative YUYV format tops out around 5 frames a second at this resolution.
  • Buffer size 1. Drivers queue frames. If we fall behind, we want the newest frame, not the one from 100 ms ago. A one-frame buffer keeps latency at the floor.

Latency from screen to array is roughly 30 to 60 ms with these cards, then a millisecond or two of our processing. Add the Arduino path and the loop reacts to a spawn in well under 100 ms.

3.3 Colour and HSV

BGR is how pixels arrive, but it is a poor space for asking "is this purple". Brightness is spread across all three channels, so the same purple at two brightness levels is two very different triples. HSV separates the questions:

H · hue
which colour, as an angle round the colour wheel. OpenCV stores it as 0 to 179, half a degree per step, so it fits in a byte. Red sits at 0 and wraps round to 179, which is why red needs two ranges.
S · saturation
how vivid, 0 grey to 255 pure. Garbage blocks are grey: bright but unsaturated.
V · value
how bright, 0 black to 255. Empty cells are dark. The ghost piece is the right hue but dim.

cv2.cvtColor(patch, cv2.COLOR_BGR2HSV) converts a patch. Then classify_patch takes the median of each channel over the patch rather than the mean. A patch on a block edge or a highlight contains a few odd pixels; the median ignores them, the mean would be pulled off.

The decision order in classify_patch is: dark means empty; bright but grey means garbage; otherwise find the hue range; if the hue matches but the value is low, it is the ghost. The order matters because a grey cell has a meaningless hue, so saturation must be checked before hue is trusted.

3.4 Cells to symbols

The screen layout is fixed at 1080p, so there is no perspective to correct: the board is a rectangle at known pixel coordinates and cell (row, col) has its centre at x = board.x + (col + 0.5) · cell_w. Layout holds these rectangles and the calibration tool lets you click them once. Had we used a camera, this is where a homography would go: a 3×3 matrix mapping the tilted quadrilateral of the screen back to a rectangle. The capture card removes the need.

read_frame produces a FrameState: a 20×10 grid of Cell symbols, the hold piece, the six queue pieces, and the garbage meter. The hold and queue boxes are identified differently from cells: the reader scans a grid of patches across each box and takes the most common piece colour, since the piece shape inside the box varies but its colour does not.

The garbage meter reader walks up the bar one cell height at a time from the bottom, classifying each patch as empty, yellow, or red, and stops at the first empty slot. Yellow segments are announced lines, red ones are committed and land at the next lock.

3.5 Symbols to game state

A frame state is a snapshot with no memory. The tracker adds memory and turns snapshots into events. Its central observation about Tetris 99 is that the next queue redraws at the exact frame a piece spawns, and the spawned piece is whatever just left the front of the queue. Detecting a queue shift is far more reliable than detecting the piece itself, which may be partly above the visible rows and can touch same-coloured cells in the stack.

At a confirmed spawn the tracker rebuilds the locked board from the frame. Line clears and incoming garbage have all resolved by then, so the visible cells are the stack plus the new piece parked near the top. If the loop predicted the board, and the frame agrees with the prediction, the leftover cells are the piece. If not, a small flood fill finds the same-coloured group in the spawn zone. Between spawns, the active piece is simply visible cells minus locked cells.

Two forms of noise are handled explicitly.

  • Debouncing. A changed queue or hold reading must be seen on two consecutive frames before it counts. A single frame with a compression artefact or a mid-redraw box does not trigger anything.
  • Our own hold press. After the bot holds, the game shows a new piece and the tracker sees a spawn. The player recognises that event as the one it caused and does not decide twice.

Hold has two visible signatures. A swap with a full slot changes the hold box and leaves the queue alone. A hold into an empty slot changes the hold box and shifts the queue by two. Both are recognised and both yield the right spawned piece and the right list of newly revealed queue pieces, which the loop forwards to Cold Clear.

3.6 Closing the loop

After each placement the player computes the board it expects: locked board plus the piece's final cells, lines cleared. At the next spawn the tracker's rebuilt board is compared with it. Equal means the presses did what the engine and Cold Clear agreed they would. Different means garbage rose, or an input was missed, or the piece kicked somewhere unexpected. Either way the response is the same: trust the screen, relaunch the bot from what is actually there, and carry on. This is the whole reason for reading the screen rather than blindly trusting the engine: every piece is a checkpoint, and no error can accumulate past one piece.

The same comparison runs offline. The fake Switch in sim_env.py renders frame states from the engine's own board, interprets the button presses independently of the executor, and the pipeline test asserts at every step that the tracker's view equals the ground truth. When the capture card arrives, the only new variable is pixels; the logic above has already been exercised end to end.

Glossary

ARR
Auto repeat rate. Once DAS has kicked in, how often the piece moves one more cell while the direction is held.
Back-to-back (B2B)
Consecutive "difficult" clears, Tetrises and T-spins, with no ordinary clear in between. Each one after the first sends extra garbage.
Bitboard
Storing each board row as an integer where bit x is column x. Makes fit tests and line clears integer operations.
Cavity / overhang / covered cell
Cold Clear's three kinds of hole damage: a sealed hole, a hole open from the side, and a filled cell that sits on top of a hole.
ctypes
Python's standard library for loading a shared library and calling its C functions with declared argument and struct types.
DAG
Directed acyclic graph. Cold Clear's search structure, a tree where identical boards reached by different orders share one node.
DAS
Delayed auto-shift. Hold a direction and, after a delay, the piece keeps moving on its own until it hits something.
Descriptor
A binary table a USB device hands the host during enumeration describing what it is: identity, interfaces, and for HID, the report layout.
Enumeration
The sequence of descriptor reads a USB host performs when a device is plugged in.
Generation
One layer of Cold Clear's DAG: all the boards reachable after placing a given number of pieces.
Ghost piece
The dim outline showing where the current piece would land if hard-dropped.
HID
Human Interface Device, USB class 3. Keyboards, mice, gamepads. Defined by a report descriptor plus a stream of fixed-layout reports.
HSV
Hue, saturation, value. A colour space that separates "which colour" from "how vivid" and "how bright".
Kick
One of the alternative offsets SRS tries when a rotation collides.
MJPG
Motion JPEG: each frame compressed as a JPEG so 1080p60 fits over USB 2.
Monte Carlo tree search
Growing a search tree by repeatedly walking from the root to a leaf with randomised, value-biased choices, expanding the leaf, and propagating scores back up.
Sonic drop / soft drop
Moving the piece straight down to the floor without locking it, so it can still move or rotate. Hard drop locks immediately.
Speculation
Searching past the known queue by branching on every piece the 7-bag could still produce and averaging.
SRS
Super Rotation System, the rotation and kick rules used by guideline Tetris games including Tetris 99.
T-spin
Rotating a T piece into a slot it could not drop into, then clearing lines with it. Sends as much garbage as a Tetris for a double.
Transposition
Reaching the same position by different move orders. Merging them is what makes Cold Clear's graph a DAG.
V4L2
Video for Linux 2, the kernel interface capture cards and webcams expose as /dev/videoN.
VID / PID
USB vendor and product identifiers, 16 bits each, the primary way a host recognises a device model.
Well
A deliberately kept empty column, usually one, that an I piece or a T-spin fills for a large clear.
7-bag
The randomiser every guideline game uses: the seven pieces are shuffled and dealt, then shuffled again. You never wait more than 12 pieces for an I.
